# Product rendering and delivery feedback

The Bramwell sofa's prepared AVIF family uses the same verified original and pixel widths as its existing WebP family. Quality 65 was selected after comparing leather detail against more aggressive settings. The 640-pixel candidate is 63,468 bytes versus 90,794 bytes for WebP; all five widths reduce transfer by about 28–31%. The original and existing WebP files remain unchanged. Source and output hashes, the encoding recipe and dimensions are recorded in `product-format-provenance.json` and verified in CI. `prepare-product-formats.mjs` requires an explicit known source and a cached original matching the existing provenance; it does not download or publish products.

`SafeImage` uses optional prepared AVIF only when an exact-source manifest entry exists and explicitly reviewed media renditions do not take precedence. An AVIF error falls back to WebP; existing remote proxy recovery remains bounded. A source change starts fresh retry state before paint, including a return to a previously failed source. The default terminal image is the unavailable placeholder, rather than a photograph of an unrelated vase. Explicit caller-provided fallback images remain supported.

The initial product document uses matching picture candidates and sizes. AVIF is restricted to scripting-enabled browsers in the initial markup so no-JavaScript visitors receive WebP directly. Adaptive pictures do not also receive a separate AVIF preload: the disabled-format browser test showed that such a preload could download an unused format. Ordinary WebP-only images retain their existing responsive preload. Empty images reserve the same square geometry on the server and client.

The product-format fixture uses the actual server renderer, `ProductPage`, `SafeImage`, CSS and source-bound assets with a synthetic read-only product. It tests native AVIF, disabled AVIF, 404 and corrupt responses, complete image failure, no JavaScript and empty images across three widths at DPR 1.75. Each case begins with a fresh browser cache; caching remains active during that case's server/client handoff. Healthy cases must issue one image download across the handoff. Server and client image dimensions must match. Commerce controls are replaced with inert fixture boundaries, so these results do not establish purchase eligibility.

The product delivery estimator now keeps its submit button focusable while an estimate is pending, using `aria-disabled` and `aria-busy` with a generation-based submission guard. Duplicate submits do not issue additional estimates. Editing the destination permits a new request, and an older completion cannot unlock that newer request. Errors retain the existing validation-summary behavior. No focus is forcibly moved back after success.

The delivery fixture uses the actual estimator, quote form, storefront CSS and fonts with synthetic read-only responses. It covers parcel/LTL displays, quote-required destinations and quantities, pack and ZIP validation, unavailable and project-only states, service errors, stale responses and pending-button focus at 320, 390, 844 and 1440 pixels. Quote forms are opened but never submitted. These are UI contracts, not carrier quotes, supplier inventory evidence, authenticated trade authorization or payment tests.

Deployment acceptance still requires exact-preview/production checks and the complete fixed-release Lighthouse audit. Local size reductions and fixture passes do not themselves establish the final production performance score.
